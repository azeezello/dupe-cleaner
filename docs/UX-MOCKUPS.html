Тёмная тема — единственная и намеренная (см. Р10 в docs/DECISIONS.md). Данные ниже синтетические, но объём — из реального прогона: 8814 групп / 6000 в быстром / 36 386 файлов.

Экран 1 · Запуск скана

Тот же функционал, что уже есть (переключатель «Быстро / Полно», задача 7), но выбор режима — не строчка радиокнопок, а две карточки: их проще ударить с первого взгляда, и выбранная видна из другого конца комнаты.

✓ Ни один режим не теряет файлы. Разница — в охвате, не в надёжности: в карантин в обоих случаях уходит только подтверждённое байт-в-байт. Начали с быстрого — можно досчитать до полного позже, не сканируя заново.
Почему карточки, а не радиокнопки. Раньше — обычный <input type="radio"> со скромной подписью; выбор было легко пропустить взглядом, хотя это самый важный переключатель на экране (Р7). Карточка целиком кликабельна/фокусируема, а разница «что произойдёт» читается без прищура. Cтрока замера времени (мс/мин) — не выдумка: цифры берутся из последнего реального прогона на этой машине, не «около».

Но сами четыре числа уже есть в отчёте (задача 4) и ничего не стоят на этом экране: без них полностью избыточный архив, который давно можно было бы убрать одним нажатием, попросту невидим.

Экран 3 · Сетка дублей — полный режим (с превью)

Одна плитка = одна группа, не одна плитка на копию. Внутри группы точных дублей копии побайтово одинаковы (Р8) — показывать одно и то же изображение два-три раза подряд не добавляет информации, только удлиняет скролл в 2–3 раза на 8814 группах.

Синтетические данные для демонстрации виртуализации — 0 плиток
отмечено в карантин 📁 — именованная папка хранит копию (Р8) 🗓 — датированная папка рез. ↓ / резкость ↓ — метрика качества из индекса (задача 9), информационно
Клик/Enter по плитке не открывает модалку — он разворачивает мини-панель на месте (пути всех копий, «Сверить полностью»), не ломая позицию скролла в сетке. Это часть ответа на «решение за секунду»: раскрытие ничего не грузит с сервера заново, кроме одной проверки по требованию.

Путь хранителя — это keeper_display_path с сервера (Р8), макет не пересчитывает «самый короткий путь» в браузере — та самая ошибка, которую задача 6 нашла и исправила в текущем app.js.

Экран 4 · Сетка дублей — быстрый режим (без превью)

В быстром режиме превью не строятся вовсе (задача 7) — 6000 плиток не должны выглядеть как 6000 серых прямоугольников. Вместо фотографии — карточка с тем, что реально известно без чтения байт: расширение, число копий, объём, путь хранителя.

Синтетические данные — 0 плиток, без превью
Почему не «серый прямоугольник + подпись». Верхняя половина плитки красится по категории файла (изображение / видео / прочее) и несёт моноширинное расширение крупным начертанием — это не декорация, а способ разом видеть состав сетки боковым зрением, пролистывая тысячи карточек: сплошная полоса одного цвета — однородный участок (например, RAW с одной камеры), пестрота — смешанный. Серый бы этого не показал.

Макет намеренно не выдумывает превью «как будто» — это противоречило бы принципу брифа «честность в цифрах»: раз файл не читался, ничего похожего на его содержимое на экране быть не должно.

Экран 5 · Карточка архива — все четыре вердикта

Задизейблить с подписью причины — тот же принцип 5 брифа («честность в цифрах»), только про действия: видно, что есть, и видно, почему пока нельзя. «Растворение» частично избыточных архивов — отдельная, не принятая задача (см. «За пределами плана» в plan.md).

Экран 6 · Сравнение медиа — крупная пара с лупой

Отвечает на открытый вопрос брифа №4: «как показать размытость/пережатие на превью, а не только числом». На 128×128 плитке разница не видна физически — нужен крупный план и зум на общую точку кадра.

Этот экран — не для сегодняшних точных дублей (там копии побайтово идентичны, сравнивать нечего — см. экран 3). Он для группы похожих снимков (near-duplicate, задачи 13/14/17): копии реально разного качества, и здесь решается Р2 — «оставить лучшую копию» — на глаз, а не только по числу.

Лупа наведена на одну и ту же точку кадра в обеих копиях (синхронный зум, не просто увеличение всей плитки) — на превью-масштабе эти два снимка выглядели бы почти одинаково; на 100% разница в резкости и пережатии становится физически видна. Предложено оставить левую — выше на всех трёх метриках; решение всё равно подтверждает человек, автоматика только сортирует.
Почему это отдельный экран, а не режим плитки в общей сетке. Принцип 3 брифа требует разной «температуры» для разных категорий: фото — крупно и спокойно, без плотной решётки. Сравнение двух конкретных копий — операция «открыл одну группу», а не «пролистываю тысячу» — плотность здесь работает против цели, а не на неё.
