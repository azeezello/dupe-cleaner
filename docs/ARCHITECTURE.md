# Архитектура

Продуктовые решения и их обоснование — в [DECISIONS.md](DECISIONS.md).
Здесь — как это устроено в коде.

## Конвейер

```
Scanner (scanner.py)          обход дисков, включая содержимое архивов
  │                            → FileRecord на каждый файл и на каждого члена архива
  ▼
ScanIndex (storage.py)        SQLite: что нашли и что уже хэшировали
  │                            ← сюда же пишутся хэши по ходу работы
  ▼
ScanJob (jobs.py)             три фазы, прогресс, отмена, восстановление
  │  ├─ 1. обход          ← дёшево, при обрыве не жалко повторить
  │  ├─ 2. быстрый хэш    ← только файлы, чей размер совпал с чьим-то ещё
  │  └─ 3. полный хэш     ← только пережившие фазу 2
  ▼
DuplicateGroup[]              группировка делается в SQL, а не в памяти
  │
  ▼
run_quarantine (quarantine.py)  перемещает только то, что имеет право двигать
```

Слои не знают деталей друг друга: `Scanner` ничего не знает про хэши,
`dedupe` — про карантин, `quarantine` — про то, как нашли дубликаты. Это и
позволяет заменить любой слой по отдельности: например, добавить в `dedupe`
поиск похожих (не идентичных) снимков, не трогая ни сканер, ни карантин.

## Почему индекс на диске, а не словарь в памяти

Скан диска на терабайты идёт часами. Первая версия держала результат в
памяти процесса: обрыв — и всё заново. Сейчас каждый вычисленный хэш
уезжает в SQLite пачками (см. `COMMIT_EVERY_FILES`), поэтому при падении
теряется в худшем случае несколько секунд работы.

Кэш действителен, пока неизменны размер и mtime **реального файла на
диске**, из которого хэш получен. Для файла внутри архива это сам архив:
перепаковали архив — все хэши его содержимого автоматически считаются
устаревшими. Логика этого инвалидации живёт в одном месте — в `ON CONFLICT`
внутри `upsert_files` и в константе `_HASH_IS_FRESH`.

Строки помечены идентификатором скана, который их последним видел, поэтому
результат всегда считается по тому, что этот скан реально нашёл, а удалённые
с прошлого раза файлы не могут воскреснуть фантомными дубликатами.

## Воронка хэширования

Три ступени, каждая платит только за то, что не смогла отсечь предыдущая:

1. **по размеру** — бесплатно, размер уже известен после обхода;
2. **быстрый хэш** — читает 64 КБ с начала и 64 КБ с конца, только для файлов, чей размер совпал хоть с чьим-то;
3. **полный хэш** — читает файл целиком, только для тех, кто совпал и по размеру, и по быстрому хэшу.

Файл с уникальным размером не читается вообще никогда.

### Тонкость, которая ломается молча

Быстрый хэш обычного файла берётся перемоткой к концу файла. Поток из
архива перематываться не умеет, поэтому для членов архива используется
последовательный однопроходный вариант — но он обязан давать **бит в бит
тот же** результат, иначе файл внутри `.zip` перестаёт попадать в одну
группу с тем же файлом, лежащим на диске россыпью. Ровно это и есть
заявленный поиск «вперемешку», и сломаться он может незаметно: все
остальные тесты при этом продолжают проходить. Равенство двух вариантов
зафиксировано отдельным тестом (`test_sequential_quick_hash_matches_the_seeking_one`).

Побочная выгода: член архива всё равно распаковывается целиком, поэтому
оба хэша считаются за один проход, и до третьей фазы он доходит уже с
готовым ответом.

### Миниатюры пристёгнуты к полному хэшу, а не к отдельному проходу

Для обычного (не архивного) фото, дошедшего до полного хэширования,
`dedupe.run_full_stage` сразу же — best-effort, ошибка декодирования не
роняет скан — кладёт в кэш миниатюру, ключ которой это тот же
`full_hash`, что уже используется для группировки. Кэш и то, почему
достаточно именно этого хэша, что ограничивает его рост и что происходит
при карантине — в `thumbnails.py` и решении Р9 (`DECISIONS.md`). Члены
архивов миниатюр не получают — см. докстроку
`dedupe.hash_archive_members`.

### Почему xxh3, а не sha256

Защита от намеренной подделки здесь не нужна — файлы принадлежат одному
человеку. Нужна скорость на больших видео, а xxh3 быстрее в разы.

## Прогресс

`ScanProgress` сознательно сообщает прогресс **по фазам**, а не одной общей
цифрой. Стоимость фаз несопоставима (обойти 500 тысяч файлов дёшево,
прочитать 300 ГБ — нет), поэтому единый «47%» был бы догадкой, поданной как
факт. Вместо этого каждая фаза сообщает то, что действительно знает: обход —
счётчик и текущую папку (общее число ему неизвестно по определению),
фазы хэширования — точный процент, скорость и ETA, потому что множество
кандидатов известно до начала фазы.

Отдельно отслеживается «залипание»: если ничего не менялось дольше
`STALL_SECONDS`, интерфейс показывает, на каком файле застряли. Для сетевых
дисков и сбойных секторов это полезнее бесконечного спиннера.

## Веб-слой

Скан выполняется в рабочем потоке (`ScanJob`), HTTP только запускает задачи,
отдаёт прогресс и результат. Закрытие браузера или перезапуск сервера не
уничтожают проделанную работу — она в индексе, а не в памяти процесса.
`ScanRegistry` держит задачи адресуемыми по идентификатору.

`/api/thumbnail` в первую очередь отдаёт файл из кэша миниатюр
(`FileResponse`, без обращения к Python-декодеру); декодирование на лету —
только запасной путь для контента, до которого скан ещё не дошёл, с
попутным сохранением результата в кэш, если хэш содержимого уже известен.
