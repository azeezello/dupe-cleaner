# Архитектура

## Конвейер (Фаза 1)

```
Scanner            ─▶  FileRecord (обычный файл или член архива)
  │  (scanner.py)
  ▼
find_duplicate_groups   группировка: size → quick_hash → full_hash
  │  (dedupe.py)
  ▼
DuplicateGroup[]    группы побайтово идентичных файлов
  │
  ▼
run_quarantine       перемещение НЕ-медиа, НЕ-архивных дублей в карантин
  │  (quarantine.py)          + отчёт (manifest.json) по остальным
  ▼
Карантин + отчёт (веб-интерфейс или CLI)
```

Каждый модуль намеренно не знает о соседних деталях реализации — `Scanner`
отдаёт `FileRecord`, ничего не зная о хэшах; `dedupe` ничего не знает про
карантин; `quarantine` ничего не знает, как были найдены дубликаты. Это
позволяет тестировать (и в будущем — заменять) каждый слой независимо,
например добавить в `dedupe` near-duplicate группировку, не трогая scanner
или quarantine.

## Почему архивные файлы — отдельная категория

Файл внутри `.zip/.tar/.7z/.rar` физически не может быть "перемещён" сам по
себе — архив пришлось бы полностью пересобрать без этого файла. Это
операция с ненулевым риском (прерывание на середине испортит весь архив), и
она плохо сочетается с моделью "переместить в карантин = обратимо
скопировать назад". Поэтому текущая версия только *обнаруживает* дубликаты
внутри архивов (и «вперемешку» между архивом и обычными файлами) и
предлагает рекомендацию, а не выполняет запись в архив автоматически. Если
это станет узким местом на практике, следующий шаг — пересборка архива
через временный файл с последующей атомарной заменой (`os.replace`), что
стоит делать отдельной, явно запрашиваемой командой.

## Почему медиафайлы — отдельная категория

Ключевое требование проекта: никогда не потерять уникальный кадр или видео.
Даже когда два файла побайтово идентичны, это не всегда обозначает
"безопасно удалить один из них не глядя" в контексте личного фотоархива —
например, если это единственная копия важного момента, а второй файл на
самом деле служебная копия с других задач (напр. вложение в переписке).
Поэтому медиа-дубликаты по умолчанию не попадают в карантин, пока это явно
не подтверждено (`confirm_media=True` / чекбокс в UI после просмотра
превью).

## Хэширование: xxh3, не sha256

Используется `xxhash.xxh3_128`, а не криптографический хэш. Здесь не нужна
защита от намеренной подделки — файлы принадлежат одному человеку — а
скорость на больших видео (десятки ГБ) имеет значение. Двухступенчатая
схема (см. `hashing.py` и `dedupe.py`) дополнительно снижает объём чтения:
большинство "случайных совпадений по размеру" отсеивается уже на этапе
`quick_hash` (чтение первых/последних 64 КБ), не требуя полного чтения.

## Веб-интерфейс

FastAPI-приложение, состояние сканов хранится в памяти процесса
(`_SCANS` dict) — это осознанное упрощение для однопользовательского
локального инструмента: перезапуск сервера просто требует повторного
скана (он быстрый благодаря двухступенчатому хэшированию), а результаты
карантина в любом случае персистентны на диске (`manifest.json`), а не в
памяти сервера.
